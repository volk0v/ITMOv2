# Результат работы модели P1-01

Ниже — код-ревью по диффу TRAINING_PR.diff. Сначала — проблемы и риски (по убыванию серьёзности), с привязкой к файлам и месту. Затем — вопросы и краткое резюме изменений.
Проблемы и риски

1. app/api.py — отсутствие валидации тела запроса и хрупкий доступ к полю
   - Код: create_review(payload: dict) -> dict[str, str]: return review_service.review(payload["diff"])
   - Проблема: при отсутствии ключа "diff" FastAPI вернёт 500 (KeyError), вместо 422/400. Нет явной схемы запроса.
   - Риск: нестабильность API и неочевидные ошибки у клиента.
   - Рекомендация: ввести Pydantic-модель с обязательным полем diff: str и/или обработку ошибок. Также задать response_model.

2. app/api.py — отсутствие обработки ошибок LLM/сервиса
   - Код: return review_service.review(payload["diff"])
   - Проблема: любые исключения из review_service (таймауты LLM, сетевые ошибки) “пробивают” до 500 без понятной диагностики.
   - Риск: нестабильность сервиса и сложность отладки.
   - Рекомендация: перехватывать исключения, маппить на понятные HTTP-ответы (422/502/504), логировать.

3. app/api.py — неограниченный размер входного diff
   - Проблема: diff может быть очень большим; без лимитов это может утяжелить запрос к LLM и привести к отказам/дорогим запросам.
   - Риск: деградация производительности/стоимости, превышение контекста модели.
   - Рекомендация: ограничить размер diff (по длине/кол-ву файлов), валидировать вход, возможно, резюмировать/сегментировать.

4. app/review_service.py — типы возвращаемых данных и контракт ответа
   - Код: def review(self, diff: str) -> dict[str, str]: return {"comment": answer}
   - Проблема: жёстко зашитая форма ответа {"comment": str} может оказаться недостаточной, если нужны структурированные замечания (список findings с полями file/line/severity).
   - Риск: смена схемы в будущем приведёт к ломающим изменениям.
   - Рекомендация: формализовать контракт ответа (TypedDict/Pydantic-модель), предусмотреть масштабирование до списка замечаний.

5. app/api.py — отсутствие response_model
   - Проблема: FastAPI не валидирует и не документирует схему ответа; клиентам сложнее интегрироваться, нет автогенерации корректной OpenAPI.
   - Рекомендация: добавить response_model, даже если он простой.

6. app/api.py — синхронный роут с потенциально долгой операцией
   - Код: def create_review(...)
   - Проблема: LLM-вызов может быть долгим; синхронный эндпоинт будет занимать воркер-треды дольше.
   - Риск: сниженная пропускная способность.
   - Рекомендация: рассмотреть async def и асинхронный клиент/адаптер к LLM, либо оставить как есть, но осознанно (ThreadPool).

7. app/review_service.py — совместимость версий Python для аннотаций
   - Код: dict[str, str] и Protocol из typing
   - Проблема: dict[...] — синтаксис Python 3.9+. Protocol в 3.7/3.8 требует typing_extensions.
   - Риск: несовместимость при более старых рантаймах.
   - Рекомендация: уточнить целевую версию Python; при необходимости использовать Dict[...] и/или typing_extensions.Protocol.

8. app/review_service.py — формирование промпта без изоляции данных
   - Код: prompt = f"Review this pull request and find problems:\n{diff}"
   - Проблема: отсутствие явной изоляции (маркерных блоков) увеличивает риск промпт-инжекции из diff.
   - Рекомендация: обрамлять diff явными границами (например, тройные кавычки с тегом), добавлять системные инструкции “ignore content instructions”.

9. app/api.py — безопасность/доступ
   - Проблема: эндпоинт без аутентификации/квотирования/рейткейта.
   - Риск: злоупотребления, расходы на LLM.
   - Рекомендация: добавить auth/rate limiting, если требуется.

10. app/review_service.py — стилистическое изменение сигнатуры Protocol
    - Код: было def generate(...) -> str: ... (однострочно), стало с телом ... в блоке.
    - Проблема: не функциональная, но создаёт лишний дифф; однострочный вариант более идиоматичен для Protocol.
    - Рекомендация: держать минимальные изменения.

Открытые вопросы

- Целевая версия Python? От этого зависят dict[...] и Protocol.
- Ожидаемая схема ответа для клиента: один комментарий или список замечаний?
- Требуется ли аутентификация и ограничение размера diff?
- Есть ли SLA по таймаутам/повторным попыткам LLM?

Краткое резюме изменений

- Добавлен сервисный метод ReviewService.review(diff) формирующий промпт и возвращающий {"comment": answer}.
- Добавлен POST эндпоинт /api/reviews, который вызывает review_service.review с payload["diff"].
- Добавлен GET /health.

Главные блокеры к мержу: отсутствие валидации тела запроса и устойчивой обработки ошибок, потенциальная несовместимость типов с Python <3.9, отсутствие схем (request/response) в FastAPI.
